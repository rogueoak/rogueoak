# 0014 - Site icon set: favicon, touch icon, and manifest icons

## Problem

rogueoak.com ships exactly one icon: `src/app/icon.svg`. That covers a modern browser tab and
nothing else, so every other place a site's identity shows up falls back to a blank page glyph or
the first letter of the URL.

- **No `favicon.ico`.** Safari, older browsers, feed readers, link unfurlers, and a long tail of
  crawlers request `/favicon.ico` directly. rogueoak.com returns a 404 to all of them.
- **No `apple-icon.png`.** No `<link rel="apple-touch-icon">` is emitted, so a Safari bookmark,
  a Reading List entry, and an iOS home screen tile all render a screenshot of the page instead
  of the mark.
- **The manifest lies about its icons.** `manifest.ts` declares `/rogueoak-avatar.png` as
  `512x512`; the file on disk is 1024x1024. It also offers no `maskable` icon, so Android crops
  the full-bleed square inside its own mask and clips the outer nodes of the oak.
- **The mark is not drawn for small sizes.** The art sits in roughly 43 percent padding, tuned for
  a GitHub avatar. Rasterized to 16px it collapses into an unreadable smudge, which is exactly the
  size a bookmark bar and a history list use.

This is for the person who bookmarks rogueoak.com, opens their history, or pins the site to an iOS
home screen, and wants to recognize it at a glance.

## Outcome

- `https://rogueoak.com/favicon.ico` returns a real multi-resolution icon (16, 32, 48).
- Every page emits `<link rel="apple-touch-icon">` pointing at a 180x180 PNG, so Safari bookmarks
  and iOS home screen tiles show the oak.
- The web manifest lists icons whose declared sizes match the bytes on disk, including a
  `maskable` variant that survives Android's mask without clipping.
- The oak reads as an oak at 16px. The icon art is reframed so the mark fills the tile rather than
  floating in avatar padding.
- Regenerating the whole set after an art change is one command: `npm run icons:build`.
- The set cannot silently drift: a `node --test` file asserts every icon the manifest references
  exists on disk at the size it claims.

## Scope

**In**

- **Reframe `src/app/icon.svg`.** Scale the mark (glow, branches, nodes) by 1.35 about its own
  center so it fills about 78 percent of the 512 frame instead of 57. The full-bleed background
  rect and the gradients are untouched. This file becomes the single source the raster set is
  built from.
- **New generator `scripts/build-icons.mjs`**, wired as `npm run icons:build`. Rasterizes
  `src/app/icon.svg` with `sharp` and writes every output below. Includes a small ICO encoder
  (PNG-in-ICO container, about 30 lines) so no ICO dependency is needed.
- **New committed outputs:**
  - `src/app/favicon.ico` - 16, 32, 48 in one file. Next's file convention serves it at
    `/favicon.ico`.
  - `src/app/apple-icon.png` - 180x180. Next emits the `apple-touch-icon` link.
  - `public/icons/icon-192.png`, `public/icons/icon-512.png` - manifest install icons.
  - `public/icons/icon-maskable-512.png` - rendered from `public/rogueoak-avatar.svg`, whose
    original padding already is the safe zone a maskable icon wants.
- **New import-free leaf `src/lib/icons.ts`** exporting the manifest icon list (src, sizes, type,
  purpose). `manifest.ts` reads it instead of hardcoding, and the test reads the same list.
- **`manifest.ts`**: consume `src/lib/icons.ts`. The mislabelled `/rogueoak-avatar.png` entry goes
  away.
- **`sharp` added as an explicit `devDependency`.** It is already resolved as a transitive Next
  dependency; the generator makes it a direct one, so declare it.
- **New `tests/icons.test.mjs`**: for every entry in `src/lib/icons.ts`, assert the file exists and
  that its PNG `IHDR` width/height match the declared `sizes`; assert `favicon.ico` is a valid ICO
  containing 16/32/48; assert `apple-icon.png` is 180x180. PNG and ICO headers are parsed with
  plain `fs` reads, no new test dependency.
- Update `docs/overview/` (features: the icon set; architecture: the generator and the icon leaf).

**Out**

- Any change to the oak artwork itself. The paths, gradients, and colors are unchanged; only the
  scale of the mark within its frame moves.
- `public/rogueoak-avatar.svg` and `public/rogueoak-avatar.png` keep their current framing. They
  are the GitHub avatar and are hard-linked by URL from `emails/templates/`, so they must not move
  or be reframed.
- A light-theme icon variant (`prefers-color-scheme` media on the icon link). The dark tile works
  on both browser themes; revisit if it reads poorly in practice.
- Open Graph and Twitter card images. Those are generated by `opengraph-image.tsx` and are a
  separate concern from the icon set.
- Per-tool and per-product favicons. rogueoak.com is one site with one identity.

## Approach

**Reframing without new art.** The mark is scaled inside the existing SVG by wrapping everything
after the background rect in a single transform group about the mark's visual center (256, 254).
The mark's bounds are roughly 286 x 294 units; at 1.35 that becomes 386 x 397 inside a 512 frame,
leaving an even margin and no clipping. Because it is a transform on the existing paths, the
vector stays one file and there is no second copy of the artwork to keep in step.

**One source, many rasters.** `scripts/build-icons.mjs` renders `src/app/icon.svg` at high density
once, then downsamples to each target with Lanczos. Rendering from the vector at every size beats
downscaling a single big PNG, and it means an art change propagates everywhere from one command.
The maskable icon is the exception and renders from `rogueoak-avatar.svg`, because a maskable icon
wants the padding the tab icon does not.

**Outputs are committed, not built.** The icons land in git as bytes. A reviewer sees them in the
PR diff, the container build stays free of an image toolchain, and a cold `next build` does no
rasterization. The script exists so regenerating is repeatable, not so CI runs it.

**Wiring is by file convention.** `favicon.ico`, `icon.svg`, and `apple-icon.png` in `src/app/`
are Next App Router file conventions; Next emits the `<link>` tags itself. No `icons` key is added
to any `metadata` export, so there is one mechanism rather than two.

**Testing.** Following the learning that regression-prone logic belongs in an import-free leaf,
the icon inventory lives in `src/lib/icons.ts` and both `manifest.ts` and the test read it. The
test parses PNG `IHDR` and the ICO directory with raw `fs` reads, so a resized or deleted icon,
or a manifest entry whose declared size stops matching the file, fails `npm test`. That is the
exact bug this spec is fixing, so it gets a test.

## Key decisions & trade-offs

- **Tighten the icon, leave the avatar alone.** The GitHub avatar and the 16px favicon have
  genuinely different framing needs, and one file cannot serve both well. Splitting them costs a
  second framing to maintain; keeping one costs an illegible favicon. The favicon wins, and the
  avatar keeps its framing because emails link it by URL.
- **Commit the binaries.** Generating at build time via `icon.tsx` would keep git clean, but
  `ImageResponse` renders through satori, which does not handle arbitrary SVG path art reliably.
  Static bytes are predictable and reviewable.
- **Hand-rolled ICO encoder over a dependency.** An ICO holding PNGs is a 6-byte header plus a
  16-byte directory entry per image. That is smaller than the code needed to justify pulling in a
  package for it.
- **`sharp` as a devDependency only.** It runs at authoring time, never at request time, so it
  stays out of the runtime image.
- **No light-theme variant yet.** Shipping two tiles doubles the set for a problem that has not
  been observed. Deferred, not dropped.
